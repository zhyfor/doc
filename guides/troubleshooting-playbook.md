# 接口排查、性能与列表设计规范

- 状态：现行约定
- 日期：2026-11-15
- 适用范围：本工作区所有接口故障、性能问题、列表/分页功能，以及需要重启运行服务的排查任务

## 1. 核心原则

1. **先定边界，再动手**：先写清目标、非目标、允许改哪些文件、完成标准；不确定的先问。
2. **先当黑盒用**：先发请求、看响应、看日志、看环境，再决定读哪段代码。
3. **概率优先**：先查最近改过、最常出错、最容易验证的地方，不追求“把所有代码看完”。
4. **投入产出比优先**：先做高概率、低成本、可验证的动作；低概率且昂贵的排查放后面。
5. **接口方案/性能方案先征求用户意见**：可能用户根本不需要这个优化，或后端有更合适的做法。
6. **重启服务必须先报告并等确认**：重启 dsh-web 等在线服务影响很大，不得擅自执行。

## 2. 动手前先定边界

### 2.1 任务边界

开始前用一句话写清：

- 要解决的问题是什么；
- 不做什么；
- 可以修改哪些文件/模块；
- 完成标准是什么（接口状态码、耗时、字段、页面行为）。

没有边界时，先向用户确认，不自行扩大范围。

### 2.2 排查边界

- 只查当前请求链路相关的代码和日志，不递归扫描整个 `node_modules`。
- 官方包、三方插件包是**最后手段**：项目自己的代码查完、日志证据仍不足时才看。
- 读源码时先看 1–2 个关键文件、按行范围读；不无边界 `grep -R` 大包。
- 每次只关注 1–2 个重要问题；连续 5 步没有新增可验证证据，就停下来复盘方向。

### 2.3 必须先征求用户意见的改动

以下情况先给方案和证据，得到确认后再改：

- 接口路径、字段、筛选语义、分页语义发生变化；
- 性能优化涉及缓存、并发、批处理、超时、降级或数据加载策略；
- 需要改动跨模块、公共函数或多个调用方；
- 问题不容易解决，需要临时绕过或引入新依赖；
- 需要重启 dsh-web、清缓存、迁移数据或改变运行环境。

**禁止“先改一版试试看”。** 方案可以带取舍和推荐，但决定权交给用户。

## 3. 先收集信息（黑盒阶段）

按以下顺序取证，先不读业务源码：

1. **错误信息**：浏览器 Console / Network、接口响应体、服务日志异常栈、失败时间点。
2. **环境信息**：进程是否在运行、监听地址/端口、是否沙箱或容器、认证态、Host/Origin、依赖服务状态。
3. **接口信息**：URL、方法、请求头、参数、HTTP 状态码、响应大小、首字节时间、总耗时、响应结构。
4. **服务器信息**：CPU/内存、磁盘、网络、最近部署/重启/配置变更。
5. **最近是否改过代码**：`git log`、`git status`、最近一次发布/重启时间。

接口黑盒测量示例：

```bash
curl -sS -o /tmp/resp.json -w 'code=%{http_code} ttfb=%{time_starttransfer}s total=%{time_total}s bytes=%{size_download}\n' \
  -b /tmp/dsh-cookies 'https://example/api?view=list'
```

先区分：没通 / 401 / 5xx / 200 但慢 / 200 但 body 空 / body 结构错误。不同结论走不同方向。

## 4. 概率排序与排查顺序

推荐按概率从高到低：

1. **最近变更**：新提交、新配置、新版本、刚重启过的服务；
2. **请求链路易错点**：认证、代理、超时、空数据、分页参数、并发、外部依赖；
3. **项目内可修改代码**：入口、路由、业务函数、数据查询；
4. **日志与运行态证据**：异常栈、慢调用、超时、资源占用；
5. **官方包/三方插件源码**：只有在前面都无法解释时才看。

“鸭子模型”要求：先用起来、看行为。例如接口很慢，先测量是网络、认证、列表查询还是序列化慢，不要一开始就翻投影缓存实现。

## 5. 打日志与验证

- 在入口和关键子调用前后加临时计时，先找占比最大的调用；
- 一次只验证一个假设，记录命令、结果、时间点；
- 找到根因后再改代码；改完回到同一现场复测；
- 临时日志和测试产物不提交仓库，验证后清理；
- 结论必须对应具体证据（URL、状态码、日志原文、耗时），没有证据只能写“推测”。

## 6. 需要用户决策时的汇报格式

```text
现状（已确认）：
- ...
关键证据：
- ...
候选方案：
A. 方案 / 成本 / 收益 / 风险
B. ...
我的建议：...
需要你确认：...
```

不要只丢一个大方案，也不要在未确认时直接改。

## 7. 重启在线服务

- 重启 `dsh-web`、生产服务、反向代理、数据库等，必须先报告：为什么重启、影响范围、预计中断时间、回滚方式；
- 得到用户明确确认后再执行；
- 执行后必须复测并报告实际结果。

## 8. 列表接口与页面展示规范

### 8.1 列表必须分页

- 所有会持续增长的列表（会话、工单、仓库、文档、日志等）必须分页；不得一次性返回全量。
- 服务端分页，前端不得先拉全量再 `slice`；只有数据量固定且很小的静态列表例外。
- 参数至少支持 `offset` / `limit`，返回应包含 `total`、`hasMore` 或等价游标信息。
- 默认页大小建议 10–50，接口必须限制 `limit` 上限，防止被大参数拖死。

### 8.2 默认过滤归档数据

- 列表默认只展示未归档数据（如 `archived=0`）。
- 查看已归档或全部数据必须显式传参（如 `archived=1` / `archived=all`）。
- 前端要有清晰的状态提示和切换入口，不能静默把归档数据混入默认列表。

### 8.3 默认排序与用户可控排序

- 默认按时间倒序（`updatedAt` / `createdAt` desc），并使用稳定唯一键作为次级排序，避免翻页重复或漏项。
- 排序参数由用户可改时，白名单校验字段和方向；非法参数回退默认排序。
- 前端翻页/筛选/排序状态应可保留（URL 或组件状态），返回后不丢失。

### 8.4 按层级展示

- 分组/父子列表默认折叠，只展示每层最近的若干项；
- 展开、翻页、查看全部要明确区分；
- 不对用户一次性铺开全部层级和全部条目。

### 8.5 性能要求

- 列表接口只加载当前页需要的数据；
- 不在列表请求中对全量数据做逐条网络请求、日志回放或昂贵 git 操作；
- 慢操作要有缓存或异步任务，但缓存方案属于性能改动，按第 2.3 节先征求用户意见。

## 9. 反例（不要重复）

- 从“接口无响应”直接翻官方包源码，最后发现只是 200 但 17 秒；
- 没有测量就改缓存/并发/超时方案；
- 一次读几十个 package、输出被截断，真正证据反而没看；
- 列表接口先全量查询再前端分页；
- 默认把归档数据混进列表，用户看不出区别；
- 未经确认重启 dsh-web。
