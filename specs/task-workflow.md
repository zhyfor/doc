# 跨仓任务工作流

- 适用：`/home/zh/www` 下跨仓、多步或涉及运行环境的任务；硬约束见根 [`AGENTS.md`](../../AGENTS.md)。
- 相关：[`project-registry.md`](project-registry.md)、[`github-collaboration.md`](github-collaboration.md)、[`operations-safety.md`](operations-safety.md)、[`documentation-rules.md`](documentation-rules.md)

## 1. 三个阶段

```text
讨论会话（想清楚） → 计划文档（写清楚） → 实施会话（按文档做）
```

- 讨论：只读代码、配置、git 状态，输出方案、边界、风险、待确认项。既定流程 bugfix 可顺手完成并同步 README/STATUS/PROJECT_INDEX（`/D` 除外）；新功能、新命令、新增运行时规则必须走计划 + 实施；复杂改动先出计划等确认。
- 计划：单仓写 `<repo>/plans/PLAN-<主题>.md`，跨仓写 `personalCloud/plans/doc/PLAN-<主题>.md`（格式见 `documentation-rules.md` §4）；写完即停，下一步给用户 `/G <绝对路径>`。
- 实施：只读计划与必要代码；编辑前确认目标仓和写权限；不重新开放式探索。

硬约束：

- 开工三问：目标仓库与入口、写权限（`test -w <目标仓>`）、交付物与验收标准是否单一；一个会话只交付一个目标。
- 前序任务提交/推送后出现新交付物、新验收标准或新环境问题，必须新开会话。
- 需求或入口未定位时只做定位，不改代码、不建目录、不装依赖；能说出目标文件、现有行为、改动点、验证方式才算定位完成。
- **`/D`·`/G` 分工**：`/D` 会话（标题以 `D:` 开头）只读代码、配置、git 状态，仅允许写 `PLAN-*.md`；禁止建仓、装依赖、改代码/配置/脚本/软链/README/STATUS/索引，禁止提交推送。选方案、给参数/阈值/预算只是计划输入，「放入计划」「你建/改 XXX」不构成执行授权。实施须同时满足：① `PLAN-*.md` 已落盘；② 用户明确说「开始」「开始实施」「按计划做」，或另开标题 `G：` 的会话。不满足只更新计划、列出待确认项后停手；禁止先改代码再补计划。
- 每 10 个工具步或每阶段汇报一次；连续 10 步无新增可验证证据即写交接并换会话；环境问题一次排查不超过两轮，只读时立即报告。
- 紧急故障、单文件低风险小修、纯查询诊断、用户明确要求跳过计划可不走三阶段，须说明原因；产生持久改动仍要更新文档和索引。

## 2. 计划文档规范

- 格式（frontmatter 三键、`## 改动记录`、状态枚举）见 `documentation-rules.md` §4；正文只写目标、范围、改动位置、实施步骤、验收、回滚，背景与复盘放 `archive/`。
- 大功能 / 新组件计划必须写明「选型结论」：选了什么轮子或为何自研（见 `engineering-rules.md` §3）。
- 可执行、可验收：写清文件路径、命令、配置项、每步产出；不写「大概」「稍后优化」，不夹带未确认方案。
- 计划即契约：实施以文档为准；计划过期或与代码不符时先停下报告。
- 篇幅默认 ≤200 行；确需保留交接证据时正文加 `## 篇幅说明`（原因、必留段落、可压缩位置），上限放宽到 400 行。
- 门禁：目标仓有文档改动时提交前跑 `./scripts/check.sh --repo <repo>`，失败不得提交；行数超限默认 WARN，`--strict` 才失败；不得用自动改文件绕过检查；检查输出路径以 `/home/zh/www` 为基准；每日巡检由 `scripts/docs-watch.sh --once` 负责，仅失败时通知。

## 3. 两层授权与开工模板

| 层 | 作用 | 不含义 |
|---|---|---|
| 工作区根 `/home/zh/www` | 能看见所有子仓库 | 不等于可改所有仓库 |
| 任务级仓库白名单 | 本次允许写哪些仓库 | 不继承到下次任务 |

`never ask` 只关闭工具弹窗，不扩大文件权限。

```text
本次可写：<repo1>、<repo2>
本次只读：其他已登记仓库
默认提交：各仓 master（无 master 用 main），直接 commit + push
```

```bash
cd <目标仓库> && git status --short
test -w . && echo writable || echo READONLY
```

未授权或不可写时立即停止，报告路径、原因和需确认事项；不得复制仓库到 `/tmp` 绕过。

## 4. 越界与扩展

```text
越界仓库：<path>
原因：<为什么必须改>
计划文件：<文件列表>
验证：<命令/结果>
请确认是否允许本次写入。
```

得到明确确认后再改；确认只对本次任务有效。多个仓的改动不得合并成一个提交。

## 5. 分支、提交与脏工作区

- 默认分支以 `repos.yaml` 的 `default_branch` 为准；非默认分支时先列当前分支、未合并提交、是否已推送，等用户选择。
- 禁止自动 merge、`push --force`、删除未提交改动；非快进时允许 `git pull --rebase origin <默认分支>` 后重推，rebase 冲突才停下报告。
- 每仓独立 `git add <明确文件>`、`commit`、`push`；禁止 `git add -A` 扫过多个仓库。
- 提交前逐仓 `git status --short`；只提交本任务文件，无关 dirty 保持原状并报告；`.bak` 等临时文件不入库；提交信息用 `type(scope): 摘要`。
- 收尾输出每仓分支、commit、push 结果、测试结果、剩余 dirty，以及「需要你执行」清单（无则写「无」）。

## 6. 排查顺序

1. **先定边界**：目标、非目标、可改文件、完成标准；只查当前请求链路，官方包/三方插件是最后手段。
2. **先当黑盒**：错误信息 → 进程/端口/容器/认证 → 请求 URL/头/参数/状态码/耗时 → 资源与最近部署 → `git log`/`git status` 取证，先不读业务源码。
3. **概率优先**：最近变更 → 请求链路易错点（认证、代理、超时、空数据、分页、并发、外部依赖）→ 项目代码 → 日志与运行态 → 官方包/插件源码；先做高概率、低成本、可验证的动作。
4. **一次只验证一个假设**：记录命令、结果、时间点；结论必须对应证据（URL、状态码、日志原文、耗时），无证据只能写「推测」。
5. **高风险先确认**：接口语义变化、缓存/并发/批处理/超时/降级、跨模块改造、临时绕过或新依赖、重启生产服务——先给方案、影响和回滚，确认后执行并复测。
6. **四句话后停止取证**：能说清「现象、根因证据、修复动作、验证方式」四句话即锁结论并进入交付，不再补读源码/日志/外部文档；结论后 ≤10 步内交付（改代码/写文档/给命令），不重复调查。长任务预计 >2 分钟的后台 job 每 60–120 秒给一条进度行（日志路径 + 当前阶段）；跨会话交接固定 3 行（已完成/未完成/下一步）。

### 6.1 环境/沙箱类问题

- 先读 DSH 会话头：`permission/preset`、`sandbox/mode`、`approval/policy`、`header.cwd`；再看 `~/.dsh/profiles/*/cordis.patch.yml` 与 `@deepseek-ai/dsh-base/cordis.patch.yml`，最后查项目规则和业务代码。
- `workspace-write` 下写根是会话 cwd；cwd 外（父仓 `.git`、`~/.dsh`、其他仓）只读是沙箱边界，不是宿主挂载，不能据此推断宿主机只读。
- 搜索错误文本先缩小范围：只用 `rg` 查目标仓/目标包，排除 `*.jsonl*`、`*.zstd`、`sessions/`、`tool-output/`、`node_modules/`、`.git/`；不递归 grep `/home/zh`、`~/.dsh` 或整个工作区。
- 写 DSH 配置优先走官方 `settings/update` API（见 [`dsh-session-automation.md`](../../personalCloud/doc/dsh-session-automation.md)）；不从沙箱内直接改 `~/.dsh`，不复制仓库到 `/tmp`。
- 改配置、重启前先跑 `./scripts/dsh-config-check.py --deep`；失败不要重启。脚本内部调用一次 `dsh --dump-config` 属正常校验。
- 整文件 `cat <<EOF` 写入易被 command-lint 拒绝；用补丁工具、`printf` 或 Python 有界写入。
- 配置改动验证：新建临时会话读首三条事件确认，再 `workspace/archiveSession` 归档；不拿交付会话反复试。

```text
候选方案：A. 方案/成本/收益/风险；B. ...
我的建议：

```

## 7. 收尾与上下文

- 压缩或换会话后以磁盘文件、git 状态为准；同目标连续 10 步无新证据或同方案连续 2 次失败，写交接并停下；会话层级最多 2 层。
- 改代码、配置、脚本或运行时规则的任务，提交前由实施会话自检（测试、门禁、真实入口回放）；**不自动派发**核验——需要独立核验时由用户 `/V`（执行核验）或明确要求后，主会话再按 `change-verify` 技能派发：只核执行结果（行为与生效性），主会话只派发与收敛、一次改动只派 1 个核验会话、默认 1 轮、报告 ≤15 行、只核 diff + 验收命令 + 计划条目且禁全仓翻查；高风险改动在派单 prompt 显式写 `verify-again` 可加 1 个核验会话/1 轮，并须在提交说明写理由；核验态的工具调用与输出上限由 `dsh-context-guard` ≥ 0.5.0 按标题 `V：`/`TODO：V：` 强制执行（默认 25 提醒 / 40 硬拒 / 单轮 20000 字符），提示词与技能不重复数字；核验会话不修任何文件，P0/P1 停手上报，修复回实施会话；结论、遗留风险与开销写入任务计划的 `## 核验记录`；P0/P1 未解决不交付（用户明确放行的例外须记入报告）。纯文档与规范文本改动不做执行核验，由计划会话自查；需要独立复核时用 `/VP`（标题 `V：计划：…`，不写快照，可反复审），同样不自动触发。两个核验技能均由 `dsh-workflow-shortcuts` ≥ 0.4.0 内置注册，入口与硬拦需配套安装。
- 收尾前更新 `PROJECT_INDEX.md`、`repos.yaml` 和目标仓文档；测试结束停服务、清端口和进程，报告资源回收依据；脚本化创建实施会话按 [`dsh-session-automation.md`](../../personalCloud/doc/dsh-session-automation.md) 执行。

### 7.1 度量（R1）

只做事后审计，不作运行时硬拦（token 与 active 只能事后算）。四个指标口径固定：

| 指标 | 口径 | 数据源 |
|---|---|---|
| active 分钟 | 相邻事件间隔 ≤300 秒的时长之和（跨过空闲不计） | `~/.dsh/sessions/*/*/session.v4.jsonl.zstd` |
| 步数 | `step/start` 事件数（回合/会话两级） | 同上 |
| 压缩后重读 | 压缩后再次读取压缩前已读过的同一 `path`/`file_path` 的调用数 | 同上 |
| 核验占比 | 标题命中 `^(?:TODO[：:]\s*)?V[：:]` 的会话数占当日会话数 | 同上 + `session/title` |

审计命令（只读，复用现有会话统计与事件）：

```bash
./scripts/session-metrics.sh --days 1        # 当日总表 + 单会话 Top 5
./scripts/session-metrics.sh --date 2026-11-22 --json
```

表内 tokens/请求/回合/工具/墙钟取自 `~/.dsh/storages/session_projcache` 的 `contextActivity`；active/步数/压缩/重读/核验取自事件明细。判定：先看区间趋势，不看单日绝对值；压缩后重读连续上升即按 `agent-action.md` §5 收紧。
